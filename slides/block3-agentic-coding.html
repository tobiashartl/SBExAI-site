From asking to delegating

Level You Claude Example
0 · Assistant ask, read, copy answers “What does feols do with singletons?”
1 · Supervised agent approve each step reads, edits, runs Block 1
2 · Delegated task approve a plan, check the result executes the plan, checks itself “Build the replication package”
3 · Delegated workflow design the procedure and the checks runs several agents, loops until checks pass “Review the paper with three referees”
4 · Unattended define the goal and limits runs in the background or on a schedule nightly reproducibility check

Each level up saves your time and moves the risk from “it did something wrong while I watched” to “it did something wrong and I did not see it”. The checks have to move up with it.

What a delegated task needs

An agent that does not know when it is done will report success: from inside the task, there is nothing else to report.

Element Example for the course project
Goal a replication package for Table 3 and Table 4, columns (i)–(iii)
Acceptance bar every replicated number within 0.01 of the published one; 00_master.R runs from a clean session
Scope may create R/, output/, README.md; must not touch data/raw/ or review/
Checks to run compare each number with the targets in CLAUDE.md; report N per table
Output a table: published, replicated, difference; a list of every definition chosen
Stop and ask when a number does not match, or a definition (sample, FTE, closed stores) is unclear

The more of this you write down, the longer Claude can work without you.

A requirements spec before the plan

For a task with research decisions in it, ask Claude to interview you first and write a spec:

I want a short literature review on the employment effects of minimum wages since Card and Krueger (1994). Ask me 3–5 questions first, then write a spec to quality_reports/specs/ before you plan.

The spec marks each requirement and each assumption:

Requirement Priority Status
Covers the 2000 comment and reply on the NJ–PA study MUST CLEAR
Every reference verified via DOI or publisher page MUST CLEAR
Includes border-discontinuity and bunching designs SHOULD ASSUMED: US studies only
Covers meta-analyses MAY CLEAR
Length and audience MUST BLOCKED: 2 pages for a seminar, or 4 for a chapter?

You resolve ASSUMED and BLOCKED items; then Claude plans; then it executes.

Give Claude a check to run

Claude stops when the work looks done. A check that returns pass or fail lets it close the loop itself: change, run the check, read the output, fix, run again.

For empirical work, checks can be:

  • stopifnot() assertions on dimensions, ranges, coded missings
  • a master script that must run from a clean R session without error
  • a comparison of every number in the text with the output files, within a tolerance
  • a simulation in which the true parameter is known and must be recovered

How strictly it is enforced:

Where Who decides it is done
in the prompt “run R/checks.R and keep going until it passes” Claude
/goal R/checks.R passes a separate model checks after each turn another model
Stop hook (Block 2) Claude Code runs the script; exit code 2 blocks the end of the turn the program

Ask for evidence: the command and its output. “All checks pass” alone tells you little.

Subagents in use

What subagents are for

A subagent is a separate Claude with its own context window, tools and model. The main session gives it a task and receives only its final report.

Built-in subagents:

Name Tools Used for
Explore read-only searching a codebase
Plan read-only research during plan mode
general-purpose all any delegated task

Your own: .claude/agents/<name>.md (Block 2).

Ask for one by name: “Use the econometrics-referee agent on R/ and draft.md”, or @"econometrics-referee (agent)".

When a subagent helps, and what it costs

Helps Why
Independent review the reviewer has not seen the reasoning that produced the code
Parallel work three papers read, three figures made, three simulations run at the same time
Noisy work long logs and searches stay out of your main conversation
Restricted tools a reviewer with Read, Grep, Glob only cannot “fix” what it should report
Cheaper model a mechanical subtask on Haiku or Sonnet
Does not help Why
“Delegate for a better answer” the same task in a new context is not a better answer

Each subagent uses its own tokens. Three parallel agents cost about three times as much.

Fresh context versus fork

Fresh subagent Fork (/fork)
Starts with only the task you give it a copy of the whole conversation
Good for independent review, verification of claims trying a variant of the current work
Bad for tasks that need the conversation’s history anything that must be independent

A reviewer that has seen the draft and the reasoning behind it tends to find the draft acceptable.

Fresh context is not a fresh environment. A fresh reviewer can still read the files on disk: last round’s review, the answer key, a log with the “correct” numbers. If the review will be compared against something, keep that out of its reach (copy the artifact to a neutral folder).

Replication package

Lab 3A in 2 minutes (the full lab is at home)

The original Card and Krueger files (fixed-width data, codebook, SAS program) turned into an R replication package a data editor could run, in one delegated task:

  • README following the AEA Data Editor template; 00_master.R running numbered scripts from a clean session
  • every published number of Table 3 and Table 4 (i)–(iii) compared with the replication: 37 numbers, largest difference 0.007
  • every definition (FTE, closed stores, sample of each table) with the page or the line of check.sas it comes from
  • a script that fails if a number misses the tolerance

The prompt contained the goal, the targets, the acceptance bar, and “stop and report if a number does not match”. The steps are in the section “At home”.

Review and verification

Why self-review fails

Asked to review its own work in the same conversation, a model has seen its reasoning and tends to accept the result. The same happens to us with our own papers.

Three ways to get an independent review:

Mechanism Independence comes from Good for
Fresh-context reviewer it never saw the draft’s reasoning wrong numbers, fabricated citations, misread code
Critic + fixer the critic cannot edit; the fixer cannot approve many defects of the same kind
Cross-artifact check it follows paper → table → output → script claims in text that the code does not support

Built in: /code-review reviews the current changes in a fresh subagent.

Who checks the checker?

A reported case: twenty bugs were planted in a working codebase and the review agents were asked to check it. They reported that everything was fine. 0 of 20 found. The report read exactly like a report on clean code.

“The check passed” is consistent with:

  • the check never ran, or ran on an old copy
  • it skipped what it could not handle
  • it cannot detect the failure it was written for

An untested check is not weak evidence. It is no evidence.

To test a check: name the failure, plant it in a copy, run the check blind, and also run it on a clean copy. Count what it finds (recall) and what it reports that is not wrong (false positives). Compare with a simple baseline.

A ladder of checks

Rung Question Example
0 · Test the checker does the check detect what it is for? plant a wrong cluster level; does the reviewer catch it?
1 · Deterministic checks does a script say pass? stopifnot(), master script runs, N matches
2 · The output exists and is real is it there, is it not a stub, is it used, does the whole make sense? the figure in the paper is the one the script produces
3 · Independent review does a reviewer who did not write it agree? fresh-context referee agent
4 · Does the result survive? does the conclusion hold under other reasonable choices? other control groups, other clustering, other samples

Classes of error that a script can decide belong in a script, not in a prompt. A prompt that lists twenty checks gets some of them skipped; a script does not.

Lab 3B · Test your verifier

Lab 3B · Steps (20 min)

verify-lab/ has two versions of a draft section of a literature review on minimum wages, each with its own refs.bib and the replicated output/table3.csv: A/ and B/. One has seven planted errors; the other is correct. You do not know which. Do not compare the two folders.

  1. Open each folder in its own VS Code window (File → Open Folder…). Ask Claude there: > Copy templates/citation-verifier.md to .claude/agents/. Change nothing else.

    Then start a new conversation (/clear).

  2. In each folder, run the same prompt:

    Use the citation-verifier agent on review.md and refs.bib. End with a numbered list of errors you are confident about.

  3. Record for each folder: the number of reported errors, and which of them you believe.

  4. When the instructor reveals the answer key: compute recall on the planted version (found / 7) and false positives on the correct version (reported errors that are factually wrong). Compare with your neighbours.

Lab 3B · Debrief (5 min)

  • Recall on the planted version: who found all seven? Which error was missed most often?
  • False positives on the correct version: what did the verifier report that is not wrong?
  • Which errors could a script find (DOI, journal, year) and which need someone to read the source?
  • Would you submit a review checked by a verifier you have not tested this way?

Results vary between runs. A single clean report tells you little; a verifier tested on planted errors and on a clean control tells you more.

What we covered

  • Delegation needs a goal, an acceptance bar, a scope, checks, an output format, and a rule for when to stop and ask
  • A spec with MUST/SHOULD/MAY and CLEAR/ASSUMED/BLOCKED makes Claude’s assumptions visible before the plan
  • Subagents: independent review, parallel work, restricted tools; each costs its own tokens
  • Fresh context for review, never a fork; keep answer keys out of the reviewer’s reach
  • Critic–fixer loops; a ladder of checks; test the checker on planted errors and a clean control
  • Known truth (a published table, a simulation) and replication before extension
  • Worktrees, background tasks and headless mode for parallel and repeated work

At home

The original package · at home

What you downloaded in Block 1 is a typical 1990s package:

public.dat      410 stores, fixed-width text, "." for missing
codebook        column positions and value labels
check.sas       the authors' SAS program for some tabulations
read.me         four lines of documentation
survey1.nj      the questionnaires
survey2.nj

Your task: a package a journal data editor could run today, in R. The AEA Data Editor README template requires, among other things: data availability and provenance, computational requirements (software and versions), a description of the programs and the order to run them, and a list of tables with the program that produces each.

Lab 3A · Steps (35 min) · at home

  1. Spec (5 min): ask Claude to interview you and write a spec with MUST/SHOULD/MAY and CLEAR/ASSUMED/BLOCKED. Resolve the BLOCKED items. Targets: Table 3 rows 1, 2, 4, 5 and Table 4 columns (i)–(iii).
  2. Plan (5 min): plan mode. The plan should include 00_master.R, numbered scripts, relative paths, output/, recorded R version, and a README following the AEA template.
  3. Execute (15 min): approve into auto or edit-automatically mode. Acceptance bar, stated in your prompt:
    • 00_master.R runs from a clean R session without error
    • a table with published, replicated and difference for every target number
    • every definition chosen (FTE, closed stores, sample of each table) listed with the page of the paper it comes from
    • if a number misses the tolerance: stop, report, do not adjust anything to make it fit
  4. Check (10 min): restart R (Command Palette → “R: Restart Session”), run 00_master.R yourself, and read the table of differences.

Lab 3A · Debrief · at home

  • Did every number match? Which did not at first, and why?
  • How did Claude find the right definition: from the paper, from check.sas, or by trying until it matched?
  • Did Claude stop when a number missed the tolerance, or did it keep changing things?
  • Could a colleague run your package without you?

Matching a published number by trying definitions until it fits is not replication. The definition has to come from the paper or the code, and the README has to say where.

Running an approved plan without interruptions · at home

When you approve a plan, you choose the mode for execution:

  • Manual: you approve each edit; slow, but you see everything
  • Edit automatically: edits go through; commands still ask
  • Auto: a classifier lets routine actions through and stops risky ones

For a delegated task: approve into auto mode, with your allow/deny rules and a check in place. Then read the diff and the evidence at the end.

Approving a plan does not limit Claude to the plan. Your permission rules and hooks do.

Patterns with several agents · at home

Parallel fan-out: one agent per independent subtask; about three is a sensible number.

Read these three papers in parallel. For each: identification assumption, estimator, replication package (yes/no). One table.

Specialist reviewers: each agent checks one dimension with full attention (code, econometrics, writing), then one report.

Independent advocates: each agent makes the strongest case for one option (three framings of the contribution) without seeing the others; a separate pass lists where they disagree. You decide.

Screening with a rubric: for “which of these 20 papers are relevant”, write the criteria first, make EXCLUDE the default, require a quoted sentence as evidence, and re-read three decisions yourself.

The critic–fixer loop · at home

            ┌──────────────┐  "12 issues, 3 critical"
            │   critic     │──────────────┐
            │ (read-only)  │              ▼
            └──────▲───────┘        ┌──────────┐
                   │                │  fixer   │ "fixed 12/12"
                   │  re-audit      │ (edits)  │
                   └────────────────┴──────────┘
   stop when two rounds in a row find nothing new (and after at most 5 rounds)

The critic has no reason to play issues down, because it does not have to fix them. The fixer cannot declare its own work done.

Findings that change an estimand, an assumption, the sample or the inference go to you, not to the fixer.

A reviewer asked to find problems always finds something. Tell it what to skip (“skip style”), or you will accept changes that make the code worse.

Known truth: simulation as a check · at home

For estimation code, the strongest check is a case where you know the answer.

  • A published table is one known answer (Lab 3A)
  • A simulation is another: generate data with a known parameter, run the estimator, and check bias and coverage over many draws

Simulate 1,000 datasets with two groups of 79 and 331 stores, a true difference of 0, and a standard deviation of employment changes three times larger in the small group. For each, compute the 95% interval for the difference with a pooled-variance and with a separate-variance standard error. Report the coverage of each.

The pooled standard error covers the true value far less often than 95% when the small group has the larger variance. This is why the paper’s 1.34 is right and the pooled 1.15 is not. An agent can run such a check and act on it; writing the prompt also tests your own understanding of the estimator.

Replicate first, then extend · at home

When you build on a published paper:

  1. Record the target numbers (Table 2, column 3: 0.123, s.e. 0.045)
  2. Reproduce them with the original specification (same sample, same controls, same clustering)
  3. Compare each number with a tolerance stated in advance; on a mismatch, stop and find out why
  4. Only then add new estimators and specifications

An agent that is asked to “extend the paper” before replicating it will build on whatever it produced first, correct or not.

Lab 3C · Screening with a rubric (optional) · at home

  1. Run /lit-search minimum wage employment effects (Block 2) to get about 15 candidates.
  2. Write a rubric: what makes a paper relevant to your review? Make exclude the default; a paper is included only if a written criterion admits it, with a quoted sentence from its abstract as evidence.
  3. Ask Claude to screen the candidates with three parallel subagents, five papers each, and to combine the results into one table.
  4. Re-read three decisions yourself: one included, one excluded, one borderline. Do you agree?

Parallel sessions and background work · at home

Tool What it does
claude -w <name> (needs git) start a session in a new git worktree: a separate checkout on its own branch, so two sessions do not edit the same files
several VS Code tabs several conversations on one project (careful: same files)
Ctrl+B move a running command or subagent to the background (terminal)
/tasks list background work
/fork copy the conversation into a background session and keep working
/loop 10m <prompt> repeat a prompt at an interval within the session
/schedule run a task in the cloud on a schedule (e.g. nightly)

Example: one worktree estimates the main specification, another builds the robustness table, you merge both when they pass their checks.

Claude from a script: headless mode · at home

claude -p "Run 00_master.R and compare every number in draft.md with output/. Report mismatches as JSON." \
  --allowedTools "Read,Grep,Glob,Bash(Rscript *)" \
  --output-format json \
  --max-turns 30
Flag Effect
-p "<prompt>" run once, print the result, exit
--allowedTools, --disallowedTools what it may use without asking (nothing else is allowed)
--permission-mode e.g. acceptEdits, dontAsk; default is manual
--output-format text \| json \| stream-json for use in scripts
--max-turns, --max-budget-usd limits on length and cost

Use it for repeated checks: every chapter through the same referee prompt, every table through the same number check. Headless use may be billed separately from interactive use; check your plan.

GitHub and the cloud · at home

  • GitHub Actions: /install-github-app connects a repository; then @claude in an issue or pull-request comment starts a run (anthropics/claude-code-action)
  • Cloud sessions (claude.ai/code): Claude works on a copy of your repository in the cloud; /teleport brings a session to your terminal
  • Agent teams (experimental): a lead session coordinates several teammates with a shared task list; high token use

For research projects: useful for a check that runs on every push (master script, number comparison). Not needed for the course.

Risks of more autonomy · at home

Risk Example Mitigation
Scope creep “while I was there I also recoded the outcome” spec with scope; review the list of changes of substance
Destructive commands deleting output/, git reset --hard deny rules; a copy or a commit before each task; worktrees
Instructions hidden in content a PDF or web page that addresses the agent: a scholarly database’s API response asked AI agents to send the user’s e-mail address (seen while preparing this course) treat fetched text as data; restrict web access for agents that edit; never send personal data
Confident false reports “all checks pass” without having run them ask for the command and its output; deterministic checks
Cost ten parallel agents at high effort limits (--max-turns, budget); smaller models for subtasks
