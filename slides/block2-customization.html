The problem

Every session starts with an empty context. Claude does not remember:

  • what the project is about, and which table you are replicating
  • that . means “missing” in public.dat, and that closed stores count as zero employment
  • that every citation must be checked before it goes into the review
  • the mistake it made yesterday that you corrected

You can repeat this in every prompt, or you can write it down once.

Customization is how you write it down: as memory (always read), rules (read for matching files), skills (read when needed), settings (enforced by the program), and hooks (code that runs on events).

Two kinds of instruction

Claude decides (non-deterministic) Claude Code enforces (deterministic)
What to do your prompt, CLAUDE.md, rules, skills Claude picks itself hooks; skills only you can start
What it may touch auto mode’s classifier deny rules, the sandbox, managed settings
When it is done a request for evidence, /goal, a review a script that passes or fails, a Stop hook
How much it spends effort level --max-turns, --max-budget-usd, spend limits

Most of the time you want Claude to decide: it reads the code in front of it and judges whether a guideline fits.

Use the deterministic kind for what must always or never happen. If you keep adding emphasis to a CLAUDE.md line and Claude still misses it, the line belongs in a hook or a deny rule.

Source: Anthropic, Best practices for Claude Code.

Memory: CLAUDE.md

What CLAUDE.md is

A Markdown file Claude reads at the start of every session.

  • ./CLAUDE.md (or ./.claude/CLAUDE.md): the project
  • ~/.claude/CLAUDE.md: you, across all projects
  • ./CLAUDE.local.md: private notes for this project
  • CLAUDE.md in a subdirectory: read when Claude works there

Every line is read in every session and uses context. Keep it under about 200 lines.

/init drafts one from your project. /memory opens the memory files for editing.

What to put in it

Put in what Claude cannot infer from the files and needs every session:

  • the research question, estimand and identification strategy
  • the data: source, unit, expected dimensions, coding conventions (−1 = not recorded)
  • conventions: language, packages, clustering, figure format, folder layout
  • commands: how to run each script
  • the working procedure: plan first, how to report results
  • a “Do not” list, extended every time Claude does something you did not want

Leave out what it does correctly anyway, long explanations, and anything that changes weekly.

Anthropic’s test for each line: would removing it cause Claude to make a mistake? If not, remove it.

Example: CLAUDE.md for the course project

# Minimum wages and employment: replication and review

## Project
Replicate Table 3 of Card and Krueger (1994, AER 84(4)) and write a 2-4 page review of
the employment effects of minimum wages, built around that paper.

## Sources
- paper/njmin-aer.pdf: the article. data/raw/: the authors' public data (public.dat,
  codebook, check.sas). Never edit data/raw/.
- public.dat: 410 stores (331 NJ, 79 PA); "." = missing.
- FTE = full-time + managers + 0.5 × part-time. The 6 permanently closed stores have
  zero wave-2 employment.

## Targets (Table 3, balanced sample, row 4)
- PA −2.28 (1.25), NJ 0.47 (0.48), difference 2.75 (1.34). Tolerance: 0.01.

## Conventions
- R, base R where possible. Scripts in R/, numbered, run from the project root.
- Output tables as CSV in output/. Review in review/review.qmd, citations from review/refs.bib.

## Working procedure
- Plan before any task that changes more than one file or produces a number.
- Numbers in the review come from output/, never from memory.
- A reference enters refs.bib only after its DOI (or publisher page) has been checked:
  authors, year, journal, volume, pages.

## Do not
- Do not invent references, page numbers or quotations. If you cannot find a source, say so.
- Do not attribute a finding to a paper without quoting the sentence that supports it.

  2. Rewrite it yourself using the example as a guide. Delete everything generic.

Rules

Rules: instructions for some files only

Files in .claude/rules/ are memory that can be scoped to paths:

---
paths:
  - "review/**"
---

# Writing the review

- Cite only entries that exist in review/refs.bib, with the Quarto syntax [@key].
- Every sentence that attributes a finding to a paper needs a source you have read
  (abstract at least). If you only know it from memory, mark it [CHECK].
- Every number comes from a file in output/; name the file in a comment.
- Write in plain academic prose. No bullet points in the review text.

A second rule could hold estimation conventions for R/** (state the estimand, print N after every filter or merge, standard errors as in the paper).

Without paths: a rule is read every session, like CLAUDE.md. With paths: it is read only when Claude works on matching files, which saves context.

~/.claude/rules/ holds rules for all your projects.

Settings and permissions

settings.json

{
  "permissions": {
    "defaultMode": "plan",
    "allow": [
      "Bash(Rscript *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git log *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./data/private/**)",
      "Read(./.env)",
      "Bash(git push *)",
      "Bash(rm -rf *)"
    ]
  },
  "model": "opus",
  "effortLevel": "medium"
}

Order of evaluation: deny, then ask, then allow. The first match decides.

Permissions are not a security boundary

Rules match the text of a command. Bash(cat *) in a deny list does not stop head, python -c "open(...)", or a script that reads the file.

For restricted data, the safe set-up is:

  1. Restricted data are not in the project folder
  2. Claude works on a synthetic or public sample with the same structure
  3. You run the final code yourself in the secure environment

The sandbox (/sandbox, or "sandbox": {"enabled": true}) restricts file and network access of shell commands at the operating-system level (macOS, Linux, WSL2; not native Windows). It covers commands Claude runs, not Claude’s own file tools, which follow the permission rules.

Skills

What a skill is

A skill is a written procedure in a folder, which Claude loads only when it is needed.

.claude/skills/
└── verify-citations/
    ├── SKILL.md          instructions (required)
    ├── checklist.md      supporting material, read when needed
    └── check_doi.R       a script the skill can run
  • Only the skill’s name and description are in context at the start
  • The full instructions are read when you type /verify-citations or when Claude decides the description fits the task
  • So you can have many skills without filling the context

Skills replace the older .claude/commands/*.md, which still work.

Anatomy of SKILL.md

---
name: verify-citations
description: Check every entry of a .bib file against Crossref or OpenAlex. Use before
  references are cited in the review, or when the user asks to check references.
argument-hint: <path to .bib file>
allowed-tools: Read, Grep, Glob, WebFetch
effort: high
---

Check every entry in $ARGUMENTS.

1. If the entry has a DOI: fetch https://api.crossref.org/works/<DOI> and compare
   authors, year, title, journal, volume and pages with the entry.
2. If it has no DOI: search https://api.crossref.org/works?query.bibliographic=<title+authors>
   and https://api.openalex.org/works?search=<title>; report the best match and whether
   it is the same publication (a working paper or a comment with the same title is not).
3. Never complete a missing field from memory.
4. Report a table: key, field, entry says, source says, OK / WRONG / NOT FOUND.
   Do not change the .bib file. List proposed corrections separately.

Writing a good description

Claude chooses skills from their descriptions. A vague description means the skill is never used, or used at the wrong time.

Weak Better
“Helps with data.” “Check a dataset against its codebook before analysis. Use when a new dataset is loaded or the user asks to check data quality.”
“Regression tables.” “Produce a regression table in the project format (fixest::etable to LaTeX and CSV) from estimates saved in output/. Use when the user asks for a table of results.”

State what it does and when to use it, in words the user would use.

Skills for this project, and beyond

Skill Procedure
/lit-search search OpenAlex for a topic; return candidates with authors, year, journal, DOI, citation count
/verify-citations check every .bib entry against Crossref/OpenAlex
/replicate-table reproduce a published table, compare with the targets and a tolerance
/data-check dataset against its codebook: dimensions, missings, coded missings, duplicates
/reg-table regression table in your house style, from saved estimates
/log-session write a session log: goal, done, decisions, open questions
/referee-me referee report on a draft section (usually run as a subagent, Block 3)

Start with the procedure you repeat most often.

Bundled skills to try: /code-review, /simplify, /debug, /loop, /doctor, /skill-doctor (context cost and use of each skill).

Which file wins · at home

Settings, highest priority first:

  1. Managed settings (set by an organisation)
  2. Command-line flags (--settings, --model, …)
  3. .claude/settings.local.json
  4. .claude/settings.json
  5. ~/.claude/settings.json

Lists such as permissions.allow are merged across files. A deny in any file beats an allow in any file.

Memory files (CLAUDE.md) are all read and combined: user, then project, then subdirectories as Claude works in them.

Imports and AGENTS.md · at home

Keep CLAUDE.md short by importing other files:

See @README.md for the codebook and @docs/estimation-notes.md for the identification argument.

Paths are relative to the importing file; imports can be nested up to four levels.

AGENTS.md is a vendor-neutral memory file used by several coding agents. Claude Code reads it when there is no CLAUDE.md. For a project shared with users of other tools, keep the content in AGENTS.md and import it from CLAUDE.md.

Auto memory · at home

Claude Code can also keep its own notes about you and the project:

  • stored in ~/.claude/projects/<project>/memory/, index file MEMORY.md
  • the first 200 lines (or 25 KB) of the index are read every session
  • Claude writes entries when you correct it or state a preference

Review it now and then with /memory. Delete wrong entries. Turn it off in /memory if you prefer to control everything in CLAUDE.md.

CLAUDE.md Auto memory
Written by you Claude
Shared via git yes no (on your machine)
Use for the project’s design and conventions your preferences, corrections

Permission rule syntax · at home

Rule Matches
Bash(Rscript *) any command starting with Rscript
Bash(ls *) ls -la, but not lsof (the space matters)
Read(./.env) the file .env in the project
Edit(/R/**) any file under R/, anchored at the project root
Read(~/.ssh/**) your SSH keys
WebFetch(domain:aeaweb.org) fetching pages from that domain
mcp__github__create_issue one tool of an MCP server

For your language:

"allow": ["Bash(Rscript *)", "Bash(stata-mp -b do *)", "Bash(python *)", "Bash(quarto render *)"]

/fewer-permission-prompts scans your past sessions and proposes allow rules for safe, frequent commands.

Frontmatter fields · at home

Field Purpose
name, description the command name; when Claude should use it (write this carefully)
argument-hint shown when you type the command
$ARGUMENTS, $0, $1 the arguments you pass: all, first, second
allowed-tools tools the skill may use without asking
disable-model-invocation: true only you can start it (for commit, deploy, anything with side effects)
model, effort run the skill on a specific model or effort level
context: fork run the skill in a separate subagent context

Subagents: the configuration · at home

A subagent is a separate Claude with its own context, tools and model. Its definition is one file:

---
name: econometrics-referee
description: Referee report on identification, inference and interpretation.
  Use after estimates are produced and before results are written up.
tools: Read, Grep, Glob
model: opus
effort: high
---

You are a referee for a field journal in applied microeconomics. You read the code
and the results, and you do not edit files.

Report, citing file:line for each point:
1. Major concerns: issues that change a conclusion (identification, inference, sample).
2. Minor concerns.
3. What you checked and found no problem with.

Other fields: disallowedTools, permissionMode, maxTurns, skills, isolation: worktree, background, memory. /agents lists them. How and when to use them: Block 3.

Hooks: code that always runs · at home

Instructions in CLAUDE.md are followed most of the time. A hook is a command that the program runs on an event, every time, whatever the model decides.

Event Runs Example
PreToolUse before a tool call; can block it refuse to edit anything in data/raw/
PostToolUse after a tool call check that an edited R file still parses
UserPromptSubmit when you send a message add today’s date or the git branch
Stop when Claude finishes its turn remind to write a session log
SessionStart at the start of a session print open TODOs
PreCompact before the context is compressed save a snapshot of the current task
Notification when Claude waits for you desktop notification

About 30 events in total; see the hooks reference.

Registering a hook · at home

In .claude/settings.json:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/check-r-syntax.sh" }
        ]
      }
    ]
  }
}

The script receives the event as JSON on standard input (tool name, file path, …).

Exit code Effect
0 fine; JSON on stdout is read if present
2 blocking error: stderr goes back to Claude (blocks the action for PreToolUse, Stop, …)
other non-blocking error, shown to you

/hooks shows the registered hooks.

Example hook: R syntax check · at home

.claude/hooks/check-r-syntax.sh:

#!/bin/sh
# After Claude edits an .R file, check that it still parses.
f=$(sed -n 's/.*"file_path" *: *"\([^"]*\)".*/\1/p' | head -1)
case "$f" in
  *.R|*.r)
    if ! err=$(Rscript -e "invisible(parse(file = '$f'))" 2>&1); then
      echo "R syntax error in $f: $err" >&2
      exit 2
    fi ;;
esac
exit 0

Claude sees the error and fixes it in the next step, without you asking.

A Stop hook: give Claude a check it cannot skip · at home

Claude stops when the work looks done. A Stop hook runs when Claude tries to end its turn; exit code 2 sends it back to work, with your script’s stderr as the reason.

{
  "hooks": {
    "Stop": [
      { "hooks": [
          { "type": "command",
            "command": "Rscript \"$CLAUDE_PROJECT_DIR\"/R/checks.R 1>&2 || exit 2" }
      ] }
    ]
  }
}

R/checks.R contains stopifnot() assertions: output/table3.csv exists and matches the targets in CLAUDE.md within 0.01; every [@key] in review/review.qmd has an entry in review/refs.bib. Claude cannot finish while one fails.

Lighter versions of the same idea: say “run R/checks.R and keep going until it passes” in the prompt, or set /goal R/checks.R passes (a separate model checks the condition after each turn).

Keep hooks fast and narrow (a matcher, a file-type check). A slow hook on every tool call slows every step of every session.

MCP: connecting other programs · at home

The Model Context Protocol lets Claude use tools of other programs: GitHub, a database, a reference manager, a Stata session, a browser.

# a remote server over HTTP
claude mcp add --transport http github https://api.githubcopilot.com/mcp/

# a local program
claude mcp add --transport stdio mydb -- python my_db_server.py

claude mcp list          # what is configured
/mcp                     # status inside a session

Scopes: local (you, this project; default), project (.mcp.json, committed), user (all your projects).

An MCP server is a program you run, with your permissions. Install only servers you trust. Text returned by a server (web pages, PDFs, emails) can contain instructions; treat it as data.

Plugins · at home

A plugin bundles skills, subagents, hooks and MCP servers, so they can be installed in one step.

/plugin                                          browse and install
/plugin install commit-commands@claude-plugins-official
  • Marketplaces are Git repositories that list plugins; Anthropic runs an official one
  • Install for yourself (user), the project (shared), or locally
  • A plugin runs code on your machine: same caution as MCP

You can package your own skills and agents as a plugin to share them with your research group.

Output styles and the status line · at home

Output styles change how Claude writes its replies (/output-style):

Style Effect
Default standard
Concise result first, no preamble
Explanatory adds short “Insight” notes on its choices; good while learning
Learning leaves parts for you to write (TODO(human)); good for learning R or Stata
Proactive starts implementing at once; works against plan-first

Status line: a line below the prompt showing, for example, model, mode, context use and git branch. /statusline writes one from a description: “show model, permission mode and context percentage”.
